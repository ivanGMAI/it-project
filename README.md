# ИТ-проект: диаграммы schemix

Набор диаграмм для описания проекта **schemix** — ИИ-ассистента, который превращает текстовое
описание бизнес-процесса в схему BPMN 2.0 (команда GoatWhistle, хакатон Интер РАО
«ИИ-ассистенты для энергетики» на Codenrock, 2026; код — `~/projects/interrao-hack`).
Все диаграммы построены по реальному коду: схеме БД (миграции `backend/migration/versions`),
модулям бэкенда и сценариям из документации проекта.

## Оформление

У всех диаграмм один стиль: шрифт Inter (имена колонок и типы в ER — JetBrains Mono), общая
палитра, заголовок с подзаголовком-нотацией и легенда на каждом рисунке, ортогональные линии со
скруглёнными углами, подписи связей на белых плашках прямо на линии.

- **Цвет несёт смысл.** DFD: процесс — синий, хранилище — бирюзовый, внешняя сущность — оранжевая,
  аналитик — фиолетовый. ER: шапка таблицы — цвет группы (документ, переписка, агент, диктовка,
  служебные), бейджи PK/FK/UQ. Чен: сущность — синяя, связь — янтарная, атрибут — белый.
  BPMN: задачи окрашены по дорожке (аналитик, браузер, сервер, агент), начальное событие
  зелёное, конечное красное, шлюзы янтарные. C4: стандартные оттенки синего, внешние системы серые.
- **ER читается однозначно:** связь выходит из шапки или верхней/нижней грани таблицы-родителя
  (ссылка на первичный ключ) и входит в строку внешнего ключа потомка; петля `runs.retry_of`
  нарисована отдельно.
- **DFD исправлена по нотации.** В Гейне–Сарсоне хранилище не может отдавать данные внешней
  сущности напрямую, поток «D5 → Аналитик» нарушал это правило. Добавлен процесс 7
  «Транслировать события» (контроллер потока событий), а вторая копия «Аналитика» внизу
  (отмечена косой чертой) убрала длинные линии через весь лист.

## Предметная область

Регламенты в энергокомпании пишут текстом, а BPMN-схемы рисуют вручную, и схема устаревает при
первой правке регламента. schemix принимает описание процесса (текст, `.docx`/`.pdf` или голос),
агент из семи ролей языковой модели извлекает участников, шаги, условия и связи, а код собирает
из этих фактов BPMN 2.0, проверяет по XSD OMG и записывает новой ревизией. Где факта не хватает,
агент задаёт вопрос с вариантами ответа; рискованные изменения ждут подтверждения человека.
Ручная правка главнее агента: результат агента применяется, только если схема не изменилась,
пока модель работала. Готовую схему выгружают в BPMN, SVG, Markdown, Word или EPC для Sila Union.

## Комментарии к связям и атрибутам

То, что на ER-диаграмме неочевидно:

- **`runs` ↔ `messages` — циклическая ссылка.** Сообщение пользователя порождает запрос
  (`runs.user_message_id`), а ответы агента ссылаются на запрос (`messages.run_id`). Оба внешних
  ключа отложенные (`DEFERRABLE INITIALLY DEFERRED`), чтобы сообщение и запрос создавались одной
  транзакцией.
- **Два номера ревизии у запроса.** `runs.base_revision` — ревизия, от которой агент начал
  работу; `runs.result_revision` — ревизия, которую он записал. Если базовая перестала быть
  текущей, результат не применяется, а запрос получает статус «устарел».
- **Один активный запрос на диаграмму.** Частичный уникальный индекс
  `uq_runs_one_active_per_diagram` по `diagram_id` для статусов `queued`, `running`,
  `awaiting_input`, `awaiting_confirmation`.
- **Ревизия — слабая сущность.** Ключ `(diagram_id, revision)`; ревизия хранит полный XML с DI
  и не меняется, возврат к старой версии создаёт новую ревизию с `restored_from`.
- **`revisions.source`** — откуда ревизия: создание, импорт, ручная правка, агент, возврат,
  диктовка, структура.
- **`proposals.preview_id`** — логическая ссылка без ограничения FK в базе (на диаграмме пунктир).
- **`dictation_segments.audio`** хранится только до распознавания фразы, затем стирается.
- **`run_artifacts`** — ответы ролей модели по их JSON-схемам с версией промпта и модели:
  по ним можно воспроизвести, что именно вернула модель.
- **`idempotency_keys`** не связана с другими таблицами: она защищает от повторной обработки
  одного и того же запроса по заголовку `Idempotency-Key`.
- **`runs.retry_of`** — рекурсивная связь: повторный запрос ссылается на исходный. В ER это петля
  у `runs`. На диаграмме Чена её нет, как и атрибута «текущий этап»: у ЗАПРОСА АГЕНТУ и так девять
  связей, и лишний ромб у него налезал на соседние подписи.

## ГОСТы и стандарты

Искал по открытым источникам, тексты ГОСТ 34.201-2020 и ГОСТ 7.32-2017 проверены по первоисточнику.

**Главный вывод: ГОСТа на ER-диаграммы, DFD, BPMN, UML или C4 нет, и нет ГОСТа, который задаёт
порядок диаграмм в документе.** ГОСТы регламентируют состав документов на систему и оформление
рисунков, а сами нотации определяются международными стандартами или первоисточниками методик.

## Проверка наложений

`node tools/check/overlaps.mjs` открывает каждый SVG в Chromium и берёт настоящую геометрию
отрисовки: размеры текста, точки линий. Находит:

- узел на узле;
- текст за рамкой своего узла;
- линию сквозь чужой узел или по тексту, в том числе по тексту таблицы, от которой линия идёт;
- подпись связи на узле, на другой подписи или перечёркнутую чужой линией;
- слипшиеся концы линий у одного узла;
- в BPMN — ещё наложение подписей пулов и дорожек.

Сейчас **все десять диаграмм чистые**. Пересечения линий друг с другом проверка не считает
ошибкой: в ER из 16 таблиц и в DFD с 29 потоками без них не обойтись, но разводка их штрафует.

## Проверки BPMN

- Все три `.bpmn` проходят XSD OMG BPMN 2.0 (схемы из `interrao-hack/backend/reference/bpmn/xsd`):
  `xmllint --noout --schema …/BPMN20.xsd diagrams/src/*.bpmn`.
- Валидатор самого schemix (`LxmlBpmnService.validate`) после перерисовки не находит ни одного
  замечания ни в режиме `draft`, ни в строгом `generated`, и файлы открываются как редактируемые.
  У каждой ветки исключающего шлюза есть условие (`conditionExpression`), этого требует строгий
  режим. Семантика процессов не менялась, пересобран только раздел `BPMNDiagram` (координаты).
- bpmn-js 18 импортирует файлы без предупреждений. Файлы можно открыть в
  [demo.bpmn.io](https://demo.bpmn.io), Camunda Modeler или загрузить в schemix и править. Цвета
  задач добавляются только при отрисовке, в самих файлах их нет.

## Как устроена сборка

```
README.md
docs/voice-notes.md          расшифровка голосовых
diagrams/
  schemix-diagrams.pdf       альбом A3 — главный результат
  png/                       рисунки 2× для Word и слайдов
  svg/                       векторные рисунки со встроенным шрифтом
  src/                       исходники:
    *.mjs                      описание диаграммы: узлы, координаты, связи, подписи
    *.bpmn                     процессы BPMN 2.0 (семантика + DI)
    *.layout.mjs               раскладка BPMN: «узел → дорожка и x», стороны входа и выхода потоков
tools/
  render.mjs                 src → svg, png
  make-pdf.mjs               svg → альбом PDF
  check/                     проверки: overlaps.mjs, contrast.mjs, readability.py
  lib/                       движок: kit (замер текста, разводка, подписи), shapes, er, chen,
                             bpmn-layout (пересборка DI), bpmn-style (bpmn-js в общем стиле)
  fonts/                     Inter и JetBrains Mono (OFL 1.1), латиница и кириллица
```

Размеры узлов считаются по реальной ширине текста (HarfBuzz по тем же файлам шрифтов, что
встраиваются в SVG), поэтому текст не вылезает за рамки. Линии разводит
[libavoid](https://www.adaptagrams.org/) — ортогонально, в обход узлов, с разнесёнными
параллельными участками. В каждый SVG встраивается только тот набор символов шрифта, который в
нём встречается.

## Пересобрать

```bash
cd tools
npm install                 # bpmn-js, libavoid-js, harfbuzzjs, subset-font, playwright, pdf-lib
node render.mjs             # все diagrams/src → diagrams/svg, diagrams/png
node render.mjs 04-dfd      # одну диаграмму
node make-pdf.mjs           # diagrams/svg → diagrams/schemix-diagrams.pdf
npm run check               # наложения, контраст, размер текста на листе
```

`PREVIEW=<папка> node make-pdf.mjs` дополнительно сохраняет PNG каждого листа PDF.

Нужен Chromium для Playwright: берётся из `CHROME_PATH`, иначе свой браузер Playwright, иначе
любой `chromium_headless_shell` из `~/.cache/ms-playwright`.

Правка исходников:

- **`.mjs`** — узлы ставятся по координатам центра (`{ cx, cy }`), размер считается по тексту.
  После правки — `node render.mjs <имя>` и `npm run check`. Если узлы стоят ближе, чем зазор
  разводки (`buffer`), линия не разведётся — `render.mjs` предупредит об этом.
- **`.bpmn`** — задачи, потоки и условия правятся в самом файле (или в BPMN-редакторе); новый
  узел нужно добавить в `<имя>.layout.mjs`, иначе сборка остановится с ошибкой. `render.mjs`
  перезаписывает раздел `BPMNDiagram` по раскладке, поэтому координаты, выставленные вручную в
  редакторе, при следующей сборке пропадут — менять их нужно в `.layout.mjs`.
